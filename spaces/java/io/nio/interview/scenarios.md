# NIO 面试实战：4 个故障场景与 3 道代码题

先独立给出排查顺序或代码，再对照下面的参考要点。本篇承接[42 道问答](./)，不额外改变问答编号。

## 四个故障场景

### 场景 A：Selector 服务 CPU 接近 100%，流量却很低

先看线程栈与循环指标：空轮询次数、select 返回值、selectedKeys 数量、任务队列、OP_WRITE 订阅数量。依次检查无数据仍关注可写、read/write 返回 0 后忙循环、selectNow 无等待轮询、EOF 未关闭或取消读关注、selectedKeys 未消费、持续 wakeup 或未处理线程中断。排除应用问题后再核对 JDK/系统版本的已知实现缺陷，不能一开始就归因于“epoll bug”。

### 场景 B：吞吐尚可，但少数慢客户端导致内存上涨

先按连接统计待发字节、输入累计字节与最老任务年龄，再看 direct memory、连接总数和业务执行器队列。确认是否只有生产，没有容量反馈。修复通常包括每连接和全局预算、高低水位、超时、最大帧长、暂停读取与拒绝策略。仅扩大堆或换成 direct buffer 不能修复无界积压。

### 场景 C：文件读取或目录遍历偶发“打开文件过多”

检查 Files.lines/list/walk/find 和 DirectoryStream 是否被关闭，是否把延迟流返回到已关闭的作用域之外，异常路径是否释放资源。再检查高并发下打开资源数量是否有上限。小测试每次都读完，不代表长期运行不会泄漏句柄。

### 场景 D：异步读取偶尔返回错乱内容或重复响应

按请求追踪 Buffer 的提交、完成、回池时间；检查超时后是否过早复用、一次部分完成是否被当成整帧完成，以及迟到回调是否修改已关闭或已复用连接。异步 Socket 还要检查同方向重复提交；异步文件允许多个操作在途，但它们不能并发共用同一 Buffer。修复依靠明确所有权与终态转换，不能单靠“回调里加 synchronized”。具体对照[异步通道第 38–40 题](./async.md)。

## 三道代码题与验收条件

### 代码题 1：手推 Buffer 状态

下面是可放在 main 中的方法体片段，需要 `import java.nio.ByteBuffer;`：

```java
ByteBuffer b = ByteBuffer.allocate(8);
b.put(new byte[] {10, 20, 30, 40, 50});
b.flip();
b.get();
b.get();
b.compact();
b.put((byte) 60);
b.flip();
```

问：最终 position、limit、remaining 和可读内容分别是什么？

答：position 为 0，limit 与 remaining 均为 4，可读内容为 `30, 40, 50, 60`。两个 get 后剩余 3 个字节，compact 将它们搬到开头并令 position 为 3；put 后为 4，flip 划定这 4 个字节。把 compact 改成 clear 会覆盖或遗失尚未消费的数据范围。

### 代码题 2：修复一次 write 后直接 clear

错误片段：

```java
buffer.flip();
socket.write(buffer);
buffer.clear();
```

**参考思路：** `write` 会推进 position，但一次调用不保证耗尽 remaining。可以让发送中的 Buffer 始终保持消费状态：有剩余时保留它及当前位置，关注 `OP_WRITE`；后续可写事件中继续发送，返回 0 就结束本轮尝试。发送完再取消写关注，随后 clear 并复用。此期间新数据必须进入另一块有界缓冲区，或暂停读取，不能覆盖待发内容。

另一种实现用 compact 把未发完数据保留到开头，恢复填充状态，下一次发送前再 flip。两种方式都可以，但不能混用状态约定。面试答案应说明循环不变量、剩余数据保存在哪、何时更新 `OP_WRITE`，以及容量不足时怎样限制输入。

完整实现可运行[有界回声服务器](../selector/server.md)，对照它的 compact 方案，用 0、8192、8193、1048576 字节及多连接验证；慢读与连接异常还需单独测。

### 代码题 3：实现长度前缀解码器

假设每帧是 4 字节大端长度加 UTF-8 正文，正文最多 1 MiB。要求处理：头部分两次到达、正文多次到达、一次多帧、空正文、负长度、超过上限、字符跨读取边界，以及 EOF 时未完成帧。

解题步骤是先收齐头部并验证长度，再等待完整正文，最后解码和交付；输入有剩余就继续解析下一帧。使用固定小缓冲区时，还需分阶段搬运到有上限的正文缓冲区，否则“大于输入缓冲区的合法帧”会永远等不齐。连接数很多时，还必须有全局内存预算；1 MiB 的单帧上限乘上连接数量可能仍然过大。

用下面的状态表检查实现，不能只验证“一次 read 刚好等于一帧”的路径：

| 当前状态 | 收到数据后怎样推进 | 何时可以交付 |
| --- | --- | --- |
| 收集 4 字节头部 | 只填剩余头部空间；未满就保存进度 | 还不能交付；头部完整后解析并校验长度 |
| 长度已验证 | 负数或超过上限立即拒绝；0 长度直接形成空正文 | 0 长度可交付，并回到头部状态继续消费输入 |
| 收集非空正文 | 按剩余长度搬运；不能把下一帧字节算入本帧 | 全部正文到齐后按 UTF-8 解码，交付并重置到头部状态 |
| 遇到 EOF | 检查是否仍有半个头部或未完成正文 | 完整帧边界可正常结束，残缺帧按协议报错 |

完整正文到齐后再统一解码，可避免将一个 UTF-8 字符分开解码；非法字节仍要按协议选择拒绝或替换策略。这里给的是实现与验收要点，完整代码由读者完成。
