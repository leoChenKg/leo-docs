# 内容与目录组织规范

本规范适用于本项目中新建、扩写、合并和重组学习文章，也适用于 AI 生成内容。目标是让读者容易找到主题、理解文章之间的关系，并沿完整的讲解掌握知识。

**以知识边界和学习任务决定结构，不以字数、行数、篇数或目录深度作为拆分指标。** 一篇完整的长文可以是良好组织；多篇必须反复跳转才能读懂的短文也可能需要合并。重组不能以减少篇幅为由删掉必要的解释、例子、边界或参考答案。

本文件负责“内容怎样划分、怎样表达”；[文档编写与 AI 协作规范](./content-authoring-guide.md)负责格式、支持语法、资源接入和验证；[项目运行手册](./project-guide.md)负责站点能力与运行方式。三者配合使用，避免维护多套相同规则。

## 1. 写作前先确定内容归属

阅读空间配置、祖先目录首页和相邻文章后，先回答这些问题：

- 目标读者是谁，已经知道什么，读完后要能解释或完成什么？
- 本文的主要问题是什么，哪些子问题必须一起讲清楚？
- 哪些知识已有专篇，新增内容应该扩写已有文章还是另建主题？
- 与前置知识、实验、工程场景和练习的关系是什么？
- 哪些内容用文字足够，哪些值得配图、表格或交互演示？

这些判断用于作者组织内容，不要求生成额外的计划文件、审批步骤或正文小节。不要先搭满目录再填充内容，也不要为了使用某个组件而反过来制造演示需求。

## 2. 目录表达主题，首页说明关系

### 何时建立子目录

当一组文章围绕同一个稳定主题，且各自承担不同学习任务时，可以建立子目录。例如一个网络专题可以包含就绪模型、服务器实验、客户端验证和工程问题。

同级目录尽量使用一致的划分维度，如技术子领域或业务任务。不要混用模糊的“其他”“补充”“更多”来收纳尚未确定归属的内容。跨主题共用的概念选择明确归属，其余文章链接过去。

只增加能帮助读者判断位置的层级。只有一个连续问题时，可以直接保留一篇文章；不必固定套用“基础 / 原理 / 实践 / 面试”四层结构，也不必为每个小节建立文件夹。

### 目录首页的职责

有明确教学范围的目录应编写 `_index.md`，说明：

- 本目录解决什么问题、适合谁，以及必要的前置知识。
- 子文章分别负责什么，推荐按什么顺序阅读。
- 不同目标的读者可以选择哪些路线。
- 哪些相关主题归相邻目录，在哪里继续阅读。

首页提供导航所需的概括，不复制各篇完整讲解。站点已自动生成子项卡片，手写链接应补充阅读关系与选择依据，避免再列一份没有解释的相同清单。

只有专题确实需要知识地图、选型概览或版本对照时才另设总览文章；如果它与目录首页承担相同职责，应合并。首页自身有必要的讲解时可以展开，不设篇幅上限。

### 命名与阅读顺序

使用稳定、具体的主题名称和小写 kebab-case 路径。标题表达文章要回答的问题，不使用“上篇 / 下篇 / 第三部分”作为唯一识别方式。

用 Front Matter 的 `order` 表达同级顺序，并在首页明确跨目录路线。侧栏、目录卡片和相邻文章导航有各自规则；当前上一篇/下一篇只连接同级普通文章，不能代替跨目录的手工阅读链接。保存后应实际检查导航，不假定文件名顺序就是页面顺序。

## 3. 文章围绕一个主要问题完整展开

“一个主要问题”允许包含多个相互依赖的子问题。例如文件复制可以同时解释读取循环、有效长度、关闭资源和中途失败；这些内容共同保证读者能写对代码，不应机械拆开。

文章根据主题选择必要组成部分：问题与目标、前置条件、核心模型、示例、解释、边界、实践选择、来源和下一步。它们是写作工具，不是每篇必须出现的固定标题清单。

每篇应做到：

- **入口明确**：读者从搜索直接进入，也知道本文讨论的对象、条件和目标。
- **论证连续**：先建立必要概念，再展示行为和原因，关键结论有例子或依据。
- **示例可理解**：区分完整程序、方法片段和伪代码，给出必要导入、版本、运行方式及预期结果。
- **边界随主题出现**：失败路径、版本差异、平台条件与常见误解放在相关机制附近。
- **出口有意义**：只链接真正的前置、深入或练习，不要求读者反复跳转才能理解当前段落。

完整实验可以单独成篇，但必须保留运行前提、代码、操作步骤、预期输出和结果解释。不要把一个程序的必要部分分散到多篇，让读者自行拼装；服务器与客户端等天然分工可分篇，并提供双向链接和启动顺序。

## 4. 按语义决定拆分、保留或合并

| 情况 | 建议处理 | 判断依据 |
| --- | --- | --- |
| 同一文章同时回答几个独立问题，读者往往只需要其中一个 | 拆为主题文章，首页解释关系 | 各篇有独立目标，拆开后仍能理解 |
| 原理与完整实验有不同查阅方式，实验还能独立运行 | 可拆为原理与实验，并相互链接 | 方便学习和复现，不破坏代码完整性 |
| 一组面试题覆盖不同主题，需要按薄弱点复习 | 按主题分组，保留总入口与题号映射 | 每组有原理回链，答案仍可独立复习 |
| 文章较长，但围绕一个问题连续推导 | 保留，改善标题、段落和图示 | 拆开会增加理解所需的来回跳转 |
| 两篇很短，反复依赖彼此才能完成同一个任务 | 合并或重新划定边界 | 独立成篇没有明确读者收益 |
| 仅因为达到某个字数、行数，或希望“目录看起来丰富” | 不据此拆分 | 数量变化不说明知识组织更清晰 |

拆分前能用一句话分别说清新文章的职责，再检查有没有内容无处归属或被重复分配。拆分后检查前置知识、相对链接、章节引用，以及“上文”“下面的两个对象”“本篇实验”等上下文是否仍成立。

## 5. 去除重复讲解，保留必要提示

同一个机制确定一篇主要讲解，其他位置用足够理解当前任务的简述加链接。版本表、长代码和详细操作步骤尽量在明确归属处维护；需要比较两种行为时，可以有目的地并列。

以下内容不应仅因“重复”而删除：

- 帮助文章独立阅读的定义、前提与关键提醒。
- 示例成立所必需的边界和失败处理。
- 题库中的直接答案、推理要点、追问或反例；不能只留下“见某篇文章”。
- 演示旁帮助读者理解输入、状态和结果的说明。

面试题集中管理后，原理文章可保留紧贴当前机制的练习，不必重复另一份完整题库。重组题库时保留题目身份和覆盖范围，明确题号变化，不能无意丢题或只保留结论。

## 6. 主动选择有解释价值的图文表达

尽量让文字、代码和视觉表达共同帮助理解。遇到结构关系、时间顺序、状态变化、空间布局或难以口述的现象时，应主动考虑图示；有明显收益时优先采用。纯文字已经清楚的内容可以保持文字，不设置每篇图片或 Demo 数量要求。

| 要解释的内容 | 优先考虑的表达 | 使用条件 |
| --- | --- | --- |
| 定义、边界、短操作步骤 | 文字、列表、代码 | 不需要为了配图再画一份相同文字 |
| API 差异、方案选择、版本差异 | 表格 | 列有统一比较维度，条件说明清楚 |
| 组件关系、流程、调用顺序 | Mermaid、可维护的示意图 | 图中关系准确，正文解释关键转折 |
| 缓冲区、内存区域、位置与状态变化 | 状态表、分步图，必要时交互 Demo | 能看出变化前后和不变量 |
| 实际界面或真实实验现象 | 截图、图片或短视频 | 真实画面比重画更有说明力，注明环境或条件 |
| 参数变化、算法步骤、因果关系 | 可操作 Demo | 读者改变输入或逐步执行能获得额外理解 |
| 测量结果与数据趋势 | 合适的图表 | 标注数据来源、单位和条件；示意数据明确标注 |

图、表或 Demo 应紧邻它解释的内容，并告诉读者重点观察什么。不要用装饰图、重复截图或无关动画填充版面；不能用一张图替代必要的解释和错误边界。

关系图优先采用便于更新的表示；需要展示真实外观或界面时选用适当的图片或截图。图片需提供准确的替代文本，必要时补充图注与来源；重要含义不只依靠颜色表达。内容放大、窄屏和深浅主题下仍应可读。

## 7. 交互 Demo 需要明确的学习收益

加入 Demo 前，应能说明：读者改变什么，观察什么变化，这比静态示例多解释了什么。如果只能点击按钮显示已经写在正文中的同一句话，通常没有必要增加组件。

适合的例子：逐步执行 ByteBuffer 的 put、flip、compact，观察 position、limit 与剩余内容；调整生产和消费速度，观察有界队列积压与背压。一次状态表已经足够解释的概念，可以只用表格。

Demo 的要求：

1. 围绕一个明确机制或实验目标，操作、观察项和解释相互对应。
2. 初始状态与重置行为明确；正常、边界和无效输入都有合理反馈。
3. 说明它是实际运行、数据回放还是概念模拟。浏览器中的 Java/NIO 状态模拟不能被描述为实际 JVM、文件系统或内核 I/O；用可运行代码或官方契约核对模拟规则。
4. 页面正文仍保留核心结论、必要代码或预期结果；演示加载失败时也能继续学习。
5. 使用项目现有 Demo 接入方式，支持键盘、窄屏和主题；对有副作用的实验明确作用范围，优先采用受控输入和隔离实验数据。

具体目录、组件与验证步骤见[Demo 模板](./templates/demo.md)和[接入规则](./content-authoring-guide.md#6-资源链接与-demo)。不要为了增加 Demo 把普通文章整体改成 MDX：普通 Markdown 也支持项目的 Demo 简写。

## 8. 重组时维护知识、代码与引用

在移动或合并前，列清原主题、重要边界、完整示例和练习分别迁往何处。删除的是不必要的重复表达，不是知识覆盖。合并重复示例时，确认仍保留必要的行为、错误路径和版本条件。

同步更新目录首页、前置/后续阅读、相邻专题、题库和资源引用。更改标题或路径还可能影响章节锚点、收藏与阅读位置，应检查旧入口是否仍有合理去向。

同名文章改成目录时，例如将 `topic.md` 迁为 `topic/_index.md`，本项目可以保留原主题页面地址；两个文件不能同时保留造成路由冲突。保留页面地址不代表旧章节锚点自动有效，也不要假设站点有未实现的重定向或别名功能。

验证力度与变更相称：仅移动、去重时先核对代码及预期输出是否完整；修改了代码行为时，再执行对应运行和边界检查。不能只凭代码围栏数量相同断言内容完整，也不能把编译成功等同于运行行为正确。

## 9. 生成与交付检查

交付时按以下问题检查质量，而不是报告“减少了多少行”作为主要成果：

- **可定位**：读者能从目录名称和首页找到需要的内容吗？
- **职责清楚**：相邻文章的目标能区分吗，通用机制有明确归属吗？
- **解释完整**：每篇的前提、推理、示例与边界是否连贯，必要实验是否可复现？
- **去重适度**：删除重复后，独立阅读、面试答案和异常语义是否仍然完整？
- **图文有效**：关系或状态难以理解时是否选用了恰当表示，每个图或 Demo 是否有解释收益？
- **链接准确**：文件、章节、资源、前后阅读与题库回链是否有效？
- **验证真实**：运行了哪些检查、覆盖了什么，还有什么未验证，是否如实说明？

网站普通 Markdown 内容至少运行 `npm run check` 并实际检查页面；MDX、Demo、媒体或图表运行 `npm run build` 并检查渲染和交互。调整目录或路径时核对旧入口与全部受影响链接，可结合 `npm run test:pages`；这些测试不能代替对具体文章链接的检查。更完整的验证要求见[编写规范](./content-authoring-guide.md#8-响应式与交付检查)。仅修改仓库维护说明时，检查文档结构、示例写法和链接即可，不必把维护文档放入网站或引入演示组件。

交付说明重点描述主题怎样重新划分、哪些内容去重或保留、阅读路线怎样变化，以及验证结果。字数和行数可以辅助观察，不设为验收目标。
